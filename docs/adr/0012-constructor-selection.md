# ADR-0012：构造器选择策略

- 状态：Accepted（2026-10-11 确认并已实施）
- 日期：2026-10-11
- 决策者：项目维护者
- 影响范围：`mini-spring-context`（`DefaultListableBeanFactory`）、`mini-spring-beans`（`@MiniAutowired` 的 `@Target`）

## 背景

原实现是"参数最多者优先；参数个数相同时按参数类型签名排序"。它有三个问题：

1. **容器在猜。** 选中哪个构造器直接决定注入哪一组依赖。猜错时不会报错——只会得到一个依赖为空、或者行为不对的对象。这属于最耗时的一类排查。
2. **使用者无法表达意图。** 即使作者心里明确"要用哪个构造器"，也没有语法能写出来，只能去调整构造器的参数个数来"迁就"启发式。
3. **同参数个数时结果任意。** 原本取 `getDeclaredConstructors()` 的第一个，而它的顺序没有规范保证。阶段 1 已把它修成"按签名排序"，但排序只解决了**可复现**，没有解决**该选哪个**。

Spring（4.3+）的规则已经被广泛接受：单一构造器直接使用；存在多个构造器时要求恰好一个标注 `@Autowired`。使用者的既有心智可以直接迁移过来。

## 决策

1. **只有一个构造器**：直接使用（包括编译器生成的隐式无参构造器），不需要任何注解。
2. **存在多个构造器**：必须**恰好有一个**标注 `@MiniAutowired`。
   - 一个都没标注 → 失败。消息列出全部候选签名，标出已标注者，并给出建议。
   - 不止一个标注 → 失败（**不**从中挑第一个）。
3. `@MiniAutowired` 的 `@Target` 增加 `ElementType.CONSTRUCTOR`。
4. 候选列表按参数类型签名排序，保证同一定义的报错内容可复现。
5. **不采用** Spring 的"多构造器且无注解时回退到无参构造器"。那个回退会把"忘了标注"这个配置错误变成运行期的行为差异——对一个以"语义可预测"为目标的库来说，这是反向的取舍。

## 后果

正面：

- 选择结果由使用者显式指定，容器不再有隐藏判断；
- 含糊的情况在**启动期**失败，并给出候选清单，不需要读源码或断点；
- 与 Spring 的心智一致（单一构造器免注解、多个需指定），降低迁移成本；
- 与 ADR-0001/ADR-0006 的取向一致：宁可在启动期响亮地失败，也不要静默地做出可能错误的选择。

负面：

- 拥有多个构造器的组件必须多写一个注解（一次性成本）；
- 对"无参构造器 + 便捷构造器"这种常见写法，使用者会先撞上一次明确报错——这是有意的，报错里会告诉他怎么改；
- 与 Spring 的细节行为不完全一致（我们不回退到无参构造器），必须在文档里写清楚，否则会被当成缺陷。

## 被否决的替代方案

1. **保持"参数最多者优先"**：继续让容器猜，且使用者没有任何表达手段。
2. **保留 Spring 式的无参回退**：隐式行为会掩盖"忘了标注"，与本次目标（语义可预测）冲突。
3. **引入 `@MiniPrimary` 式的构造器优先级**：为同一个问题再加一种机制，规则数量翻倍而收益不变；等确有需求时再单独决策。
4. **运行期按"哪个构造器的依赖都能满足"来挑**：更不可预测——同一个类在不同环境下可能选中不同构造器。

## 验收标准

1. 五种场景各有测试：唯一构造器（免注解）、唯一构造器带注解、多个构造器其中一个标注（选它）、多个构造器都未标注（失败并列出候选）、多个构造器都标注（失败）。见 `ConstructorSelectionTests`。
2. 报错消息包含候选签名与建议，且候选顺序稳定（按签名排序）。
3. **现有组件与样例在改动后无需任何修改即可通过**——已实测：改动前后 119 个既有测试与两个样例全部未改动即通过。这说明此前没有任何代码真正依赖"参数最多"这条启发式，改动是纯语义收敛。
