# ADR-0003：类路径扫描策略

- 状态：Accepted（2026-10-11 确认；阶段 1 据此实施）
- 实施：已落地（2026-10-11）。`ClassPathScanner` 用 ASM 读字节码元数据，扫描阶段不加载类；组件类以 `initialize=false` 加载，静态初始化推迟到实例化；支持 `file:`/`jar:`，嵌套 jar 显式报错；结果按类名排序。测试用"每个用例一个新 ClassLoader + 显式初始化的对照组"证明扫描确实没有初始化用户类，并断言非组件类从未被加载。
- 差异说明：决策中写的"用 ASM 的 inner-class 标志判断内部类"最终以"字节码里的类名是否含 `$`"实现（读到的类名即权威），文件名过滤只作为快速剪枝；`ClassLoader#loadClass` 已完全从扫描路径移除。
- 日期：2026-10-11
- 决策者：项目维护者
- 影响范围：`mini-spring-context`

## 背景

扫描实现位于 `MiniApplicationContext.java:138-189`，存在四个独立问题：

1. **只支持 `file:` 协议**（`:146-148`）。打成 jar 后组件全部扫不到，这是 README"当前不足"第 1 条的真实位置。
2. **顺序不确定**。`scanDirectory` 依赖 `File.listFiles()` 的顺序（`:164`），该顺序由文件系统决定。这意味着 BeanDefinition 注册顺序、启动日志顺序、以及"多个候选时哪个先被选中"在不同机器上可能不同——失败不可复现，这是真实的可维护性缺陷，不只是美观问题。
3. **扫描有副作用**。判断注解需要 `classLoader.loadClass(className)`（`:184`），而加载类会**执行静态初始化块**。一个声称"只是扫描"的只读动作因此可能触发任意用户代码；同时 `ClassNotFoundException | NoClassDefFoundError` 被静默吞掉（`:185-187`），问题被隐藏。
4. **路径拼接脆弱**。`packageName + "." + file.getName()`（`:171`）对含 `.` 的目录名与内部类处理不严谨，仅用 `fileName.contains("$")` 粗筛（`:175`）。

## 决策

**扫描阶段不加载类。** 用 ASM 读取 `.class` 字节码元数据（类级注解、访问标志、超类、接口、内部类标志）判断候选；只有确定为组件、即将注册为 BeanDefinition 的类才由 ClassLoader 加载。ASM 作为 `mini-spring-context` 的显式依赖（`org.ow2.asm:asm:9.8`，本地仓库已存在，但必须显式声明并由依赖收敛规则约束版本）。

**协议支持：** `file:` 与 `jar:` 两种 URL 协议均支持。嵌套 jar（Boot fat jar 的 `jar:file:...!/BOOT-INF/classes!/`）明确**不支持**，遇到时抛出可读异常并说明替代方案，而不是静默漏扫。

**确定性：** 扫描结果按类全限定名排序。BeanDefinition 注册顺序、启动日志、失败顺序在所有机器与所有 JDK 上一致。这是可复现性的硬要求，不提供"关闭排序"的开关。

**过滤规则显式化：** 跳过 `package-info`、`module-info`、内部类/匿名类（改用 ASM 的 inner-class 标志判断，不再依赖 `$` 字符串）；支持按包名与注解做 include/exclude 过滤，为后续条件装配留扩展点。

**性能：** 每个类文件只读取一次，元数据在同一进程内可缓存；扫描结果不可变返回。扫描耗时进入 JMH 基准（见路线图阶段 3）。

## 后果

正面：

- jar 部署可用，这是"能被别的项目依赖"的前提；
- 失败可复现，日志可对比，CI 上不会出现"本地能过、服务器不过"；
- 扫描不再触发用户静态初始化代码，行为可预测；
- 为后续按注解/条件筛选做性能优化留出空间（ASM 方案下筛选不需要加载类）。

负面：

- 引入 ASM 依赖，需要维护版本收敛与 shadow/重定位策略（使用者可能与自己的 ASM 版本冲突）；
- 需要自己处理字节码层面的细节（不同 class 文件版本的常量池差异、注解保留策略），实现成本高于反射方案；
- 需要在 ASM 元数据与反射结果之间保持一致性语义（例如注解 `@Retention(CLASS)` 的情况），这必须在文档中讲清。

## 被否决的替代方案

1. **继续用 `loadClass` 反射扫描，只补 jar 支持**：无法解决静态初始化副作用，也无法解决"扫描即加载"带来的启动开销，等于把已知问题带进 1.0。
2. **用 `Reflections` 等第三方扫描库**：能快速解决协议与过滤问题，但把核心能力外包，且该库本身也基于 ASM——不如自己掌握这层，这是一次性的可控成本。

## 验收标准

1. jar 内的组件能被扫到（构造一个含组件的测试 jar，或使用测试类路径中的既有 jar）；
2. 同一 classpath 连续扫描两次，注册顺序完全一致；在打乱文件系统枚举顺序的条件下仍一致；
3. 扫描不触发被测类的静态初始化（被测类放静态计数器，断言扫描后计数为 0）；
4. `file:` 与 `jar:` 两条路径各有测试；嵌套 jar 给出明确异常而非漏扫；
5. 含 `.` 的包名段、内部类、`package-info` 各有测试。
