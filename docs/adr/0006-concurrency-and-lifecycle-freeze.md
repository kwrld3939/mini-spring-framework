# ADR-0006：并发模型与生命周期冻结

- 状态：Accepted（2026-10-11 确认；阶段 1 据此实施）
- 实施：已落地（2026-10-11）。`freeze()` 之后定义表与单例池不可变、经 volatile 一次性发布，运行期读路径无锁；冻结后注册 Bean/BeanPostProcessor 直接报错；`lazyInit` 字段已移除（不支持即不保留字段）。销毁按依赖图逆序（依赖者先销毁），单个回调失败不中断其余并聚合为 `LifecycleException`。
- 并发验证：16 线程 × 320 次并发 `getBean`（单例同一实例、prototype 实例互不相同）作为回归；环检测依据"当前创建路径"而非共享集合，因此 prototype 的并发创建不会互相误判成环。
- 补充修正：销毁回调原先按实例的运行时类反射，被代理的 Bean 会静默跳过 `@MiniPreDestroy`（JDK 代理上甚至没有该方法）；现在按定义类反射、在**目标对象**上调用，并有回归测试与变异检验。
- 日期：2026-10-11
- 决策者：项目维护者
- 影响范围：`mini-spring-beans`、`mini-spring-context`

## 背景

容器当前是"随时可变的共享状态"，没有任何并发保护：

- 单例池是 `LinkedHashMap`（`MiniApplicationContext.java:41`），BeanDefinition 表同样（`:40`）；
- 运行期 `getBean` 会写共享状态：prototype 走 `instantiate`（`:70-72`），lazy 单例走 `getOrCreateBean`（`:191-213`，内部 `beans.put(...)`）；
- 没有 `volatile`、没有同步、没有安全发布手段。启动完成后若多个线程并发 `getBean`，存在数据竞争（`LinkedHashMap` 并发写可能损坏结构）与非安全发布（另一线程可能看到半初始化的对象）；
- `close()` 按插入顺序遍历销毁（`:360-364`），不保证"依赖者先于被依赖者"销毁——若销毁回调里用到已销毁的依赖，会得到难以理解的失败。

在单线程的演示里这些都不暴露；一旦被真实服务使用（Web 请求线程池并发取 bean），就是必现问题。所以在 v0.1 就必须把模型定清楚，而不是留到"以后加锁"。

## 决策

**明确两阶段生命周期：`refresh()`（可变，单线程约定）→ `frozen`（不可变，读无锁）。**

### 1. 阶段与不变式

| 阶段 | 状态 | 允许的操作 |
| --- | --- | --- |
| 构建中 | mutable | 注册 BeanDefinition、加载配置、注册 BeanPostProcessor |
| 刷新中（`refresh()`） | mutable，受保护 | 实例化、注入、初始化、产生代理、写单例池 |
| 已冻结（`frozen`） | immutable | 读 `getBean`、读定义、只读诊断信息 |

冻结后：

- BeanDefinition 表与单例池**不可再变更**；注册新 bean 或新 BeanPostProcessor 抛出明确异常（消息说明"容器已刷新，运行期注册不受支持"）并提供替代做法（用 `@MiniConfiguration`/`@MiniBean` 在刷新期注册）；
- 读路径无锁，通过一次性安全发布（`volatile` 引用替换为不可变视图）保证其他线程看到完整的单例池与终态对象；
- 单例对象在冻结前全部完成初始化（含代理），因此不存在"第一次 `getBean` 触发初始化"的竞争窗口。

### 2. lazyInit

**v0.1 不支持 `lazyInit`。** 当前 `BeanDefinition` 的 `lazyInit` 恒为 `false`（`:114`），保留字段会让使用者以为"支持但可能没测"。决策：从 `BeanDefinition` 移除该字段；未来若要支持，必须连同"冻结后受控的 double-checked 初始化路径 + 环检测 + 并发测试"一起作为一个独立 ADR 引入。

### 3. prototype 语义

prototype 的创建**不触及共享可变状态**：定义表只读、创建过程只用局部变量，创建出的实例不进入单例池。每次 `getBean` 返回新实例，可被多线程并发调用。

### 4. 销毁顺序

- 按依赖关系**逆序**销毁：依赖者先销毁，被依赖者后销毁（若 A 依赖 B，则 A 先销毁、B 后销毁）；
- 依赖关系由容器在创建期记录（依赖图随 BeanDefinition 一起冻结），而不是靠反射重新推断；
- 无依赖关系的 bean 之间按创建顺序的逆序销毁；
- 单个销毁回调抛异常**不中断**其余销毁，全部收集后以 `LifecycleException` 聚合抛出，消息列出失败 bean 与各自的 cause。

### 5. 并发测试

JUnit 并发测试（固定线程池 + `CountDownLatch` 同时起跑，`assertTimeout` 兜底）覆盖：

- 多线程并发 `getBean(name)` 单例：无异常，且所有线程拿到同一实例；
- 多线程并发 `getBean(prototype)`：无异常，且实例互不相同；
- 冻结后注册：抛异常且消息可读；
- 并发 `close()` 与 `getBean` 的交互按文档语义处理（约定：`close()` 不与读并发，若并发则行为未定义并在 javadoc 声明）。

## 后果

正面：

- 单例池是"启动期构建、运行期只读"，这是能被真实服务安全使用的最低前提；
- 销毁顺序符合依赖直觉，避免"用到已销毁依赖"的诡异报错；
- 移除 `lazyInit` 字段消除了"看起来支持"的假象。

负面：

- 失去运行期动态注册能力（Spring 也基本不支持，属可接受取舍）；
- 需要维护依赖图，内存与启动期成本略增；
- 冻结模型要求所有初始化都在 `refresh()` 内完成，未来若引入 `@MiniLazy` 需要重新设计（已通过"独立 ADR"约束）。

## 被否决的替代方案

1. **全部用 `synchronized` 保护**：能过并发测试，但把读路径也串行化，且没有解决非安全发布的语义问题；"冻结 + 安全发布"才是正确模型。
2. **改成 `ConcurrentHashMap` 就认为安全**：只解决结构损坏，不解决半初始化对象可见性与状态可变性，是最常见的伪修复。
3. **文档声明"容器不支持多线程"**：对一个面向 Web 的 IoC 容器来说等于放弃使用场景。

## 验收标准

1. 并发单例 `getBean` 测试通过（≥ 16 线程 × 多次迭代），断言实例同一；
2. 并发 prototype `getBean` 测试通过，断言实例互不相同；
3. 冻结后注册 bean / BeanPostProcessor 抛异常，并有测试断言消息；
4. 销毁顺序测试：A 依赖 B，断言 B 的 `@MiniPreDestroy` 在 A 之后执行；
5. 销毁回调抛异常时其余 bean 仍被销毁，异常以 `LifecycleException` 聚合且包含全部 cause；
6. `BeanDefinition` 不再暴露 `lazyInit`（编译期即被约束）。
